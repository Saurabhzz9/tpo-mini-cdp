# Security and privacy review

## Implemented controls

- `src/lib/auth.ts`: iron-session authenticated encryption, HTTP-only SameSite cookies, eight-hour expiry, production Secure flag, scrypt password verification, constant-time hash comparison, durable rate counters, exact Origin validation for mutations, streaming request-size enforcement. UI protection is repeated in protected layouts; every API request is authorized independently.
- `src/app/api/[...path]/route.ts`: role enforcement on imports and Event Lab; Zod request schemas; parameterized SQL; no public registration; bounded search, timeline, preview and export paths; audited exports. Staff share an internal workspace; segment access is workspace-wide by design, not per-owner tenancy.
- `src/lib/webhook.ts`: strict event contract, HMAC-SHA256 raw-body authentication with signed timestamp, five-minute clock tolerance, constant-time signature comparison, primary-key deduplication, conflicting content rejection, transaction-scoped advisory lock and conservative shared-device rules. Rate limiting occurs only after authentication so unauthenticated attackers cannot consume the legitimate sender's rate bucket. Body limits apply before authentication.
- `src/lib/importer.ts`: fixed CSV headers, 8 MB limit, 50,000-row limit, bounded record length, transaction rollback, raw value preservation, validation flags and deterministic identity normalization. Uploaded strings are rendered as React text; no imported HTML is executed.
- `src/lib/assistant.ts`: allowlisted intent projection, aggregate-only query layer, small-count suppression, approved source and page labels, no arbitrary SQL, no model-visible identity IDs, validated model segment arguments, inspected transport tests, timeouts and safe provider errors. Model-visible opaque segment IDs are routing references, not person IDs.
- `src/lib/segments.ts`: typed persisted predicates and formula-safe CSV quoting, including whitespace-prefixed spreadsheet formula payloads.
- `next.config.ts`: frame restrictions, nosniff, same-origin referrers, permission restrictions, no-store responses and a restrictive origin CSP. Development permits unsafe-eval solely for webpack's development runtime; production does not. Inline Next.js bootstrapping still requires unsafe-inline in the current policy.
- `Dockerfile` / `.dockerignore`: unprivileged runtime, standalone bundle, no `.env`, local credentials, source datasets or development database in the container. Hosted startup requires PostgreSQL and runs migrations before serving. `infra/main.bicep` enables HTTPS-only, TLS 1.2+, disabled FTP and explicit database IP allowlisting.

The three assessment CSVs are synthetic, as the PDF states. They are deliberately included for reproducibility. Real customer data and all credentials must remain outside Git. `.env`, local access credentials, embedded databases, screenshots and browser traces are ignored. Logs do not print webhook bodies, subscriber rows, model provider errors or connection strings.

## Tests and observed corrections

Unit/integration tests capture actual constructed model request bodies using a fake transport; names in the original question, poisoned source labels, emails, IDs and raw subscriber rows are excluded. E2E tests use isolated PostgreSQL directories, generated test-only credentials, actual signed HTTP delivery, and server authorization checks. Live Azure aggregate inference was also exercised separately; its safe result is in `docs/ai-smoke.json`.

Development verification caught an initial timestamp parser that excluded the CSV's space-separated timestamps. Raw rows were preserved; the parser now explicitly treats that format as UTC, and full source-count assertions prevent recurrence. Browser verification also caught premature native form submission before hydration; the form now uses POST and the sign-in button stays disabled until hydration. Development CSP was adjusted for webpack without adding unsafe-eval to production. These are actual implementation corrections, not invented demo anecdotes.

## Remaining risks and scope limits

1. Authentication uses environment-configured staff credentials, not SSO/MFA. Existing sessions cannot be selectively revoked; password changes alone do not invalidate them before their eight-hour expiry. Rotate SESSION_SECRET to revoke all sessions. Move to organizational identity and per-session revocation before broad staff access.
2. Production still permits inline scripts and styles for Next.js bootstrapping. React escapes imported content and there is no identified HTML injection sink, but nonce-based CSP would improve defense against future XSS. The previous global login-lockout bucket has been replaced by per-client durable limits. Hosted App Service explicitly trusts the final proxy-appended X-Forwarded-For address only when LOGIN_TRUSTED_PROXY=azure-app-service and WEBSITE_INSTANCE_ID is present. That mode requires App Service to be the sole ingress; do not enable it for a directly reachable Node server. Local direct mode intentionally shares a local bucket. Distributed attacks and clients sharing one NAT remain availability limits; this is not a full edge WAF or account lockout system.
3. Azure provisioning now uses a separate non-owner application database role with table DML and sequence usage; migrations run separately with owner credentials. The template requires an independent application password and starts the server without privileged migrations. TLS verification and three isolated network PostgreSQL transaction tests have executed successfully. Cloud HTTP acceptance is recorded separately in DEPLOYMENT.md. Backups are configured for seven days, but a restore drill remains unverified. Runtime secrets use App Service settings; organizational rollout should adopt Key Vault references/managed identity where supported.

Additional limits: fixed analytics intents prioritize privacy over unrestricted conversational coverage; outputs can contain model mistakes, so the original aggregate data is inspectable. Regex output filtering catches common email/ID forms but cannot establish that a model will never invent a person's name. No real subscriber names or rows are provided to it. Minimum-size suppression limits small groups, but does not implement a formal differential-privacy budget. One global webhook transaction lock limits throughput. Export rate limits and current dataset size bound exports, but production data growth needs query and export pagination. No independent penetration test has been performed.

## Refactor verification

The service-level event validator rejects mixed test/live event, device and user identifiers before writes. Reserved test_ app-user imports remain in raw records with an invalid-app-record flag. Import and webhook identity writes share one transaction lock, including unknown-user creation. An isolated real PostgreSQL test exercised concurrent imports/deliveries and verified no duplicate account or failed transaction. Test namespace collisions and per-client login isolation have dedicated regression tests.

An independent assistant security baseline found the shared login denial issue before its repair. Source review also found the identity namespace and cross-workflow lock correctness gaps; these were not mislabeled as anonymous privilege escalations. The Codex Security workbench scan was started and a candidate checkpoint retained, but its tools became unavailable before canonical completion. No completed plugin report, independent penetration test or unrestricted production-security certification is claimed. The implementing assistant's source review and executed tests are documented in REFACTOR_REVIEW.md.
